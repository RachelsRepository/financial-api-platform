# Architecture

## Layered design

The platform follows clean architecture with strict dependency direction:

```mermaid
flowchart TB
  subgraph interfaces
    HTTP[HTTP Controllers]
    WK[Workers]
  end

  subgraph application
    UC[Use Cases]
    PT[Ports]
  end

  subgraph domain
    EN[Entities]
    VO[Value Objects]
    PO[Policies]
  end

  subgraph infrastructure
    PR[Prisma Repositories]
    KF[Kafka Publisher]
    PV[Provider Adapters]
  end

  HTTP --> UC
  WK --> UC
  UC --> PT
  UC --> EN
  UC --> PO
  PR -.implements.-> PT
  KF -.implements.-> PT
  PV -.implements.-> PT
  EN --> VO
  EN --> PO
```

| Layer              | Responsibility                                                |
| ------------------ | ------------------------------------------------------------- |
| **Domain**         | Business rules, state machines, money, scopes — no frameworks |
| **Application**    | Orchestration via use cases; depends on ports only            |
| **Infrastructure** | Prisma, Redis, Kafka, provider HTTP, JWT signing              |
| **Interfaces**     | NestJS HTTP adapters, background workers                      |

## OAuth authorization code flow

```mermaid
sequenceDiagram
  participant Client as TPP Client
  participant API as Platform API
  participant User as End User
  participant DB as PostgreSQL

  Client->>API: GET /oauth/authorize (PKCE challenge)
  API->>DB: Persist AuthorizationRequest + Consent
  API-->>Client: consentId, state

  User->>API: POST /api/v1/consents/{id}/authorize
  API->>DB: Consent AUTHORIZED + authorization code
  API-->>User: authorizationCode

  Client->>API: POST /oauth/token (code + code_verifier)
  API->>DB: Validate PKCE, issue JWT + refresh token
  API-->>Client: accessToken, refreshToken (, idToken)
```

## PKCE

```mermaid
sequenceDiagram
  participant Client as Public Client
  participant API as Authorization Server

  Note over Client: code_verifier = random high-entropy string
  Note over Client: code_challenge = BASE64URL(SHA256(code_verifier))

  Client->>API: GET /oauth/authorize?code_challenge&code_challenge_method=S256
  Client->>API: POST /oauth/token code_verifier=...
  API->>API: verifyS256(verifier, challenge)
  API-->>Client: tokens (only if PKCE valid)
```

## AIS request (Account Information)

Account Information Service reads are **repository-backed**. The request path does not call a provider adapter.

```mermaid
sequenceDiagram
  participant Client as TPP
  participant Ctrl as AccountsController
  participant Guard as BearerAuthGuard / ScopesGuard
  participant UC as ListAccountsUseCase
  participant Consent as ConsentRepository
  participant Authz as AuthorizationDecisionService
  participant Accounts as AccountRepository
  participant PG as PostgreSQL

  Client->>Ctrl: GET /api/v1/accounts (Bearer JWT)
  Ctrl->>Guard: validate JWT + scopes
  Guard->>UC: execute(consentId, claims)
  UC->>Consent: findById(consentId)
  UC->>Authz: requireAccountAccess(accounts:read)
  UC->>Accounts: findByUserAndInstitution(...)
  Accounts->>PG: SELECT accounts
  PG-->>Accounts: rows
  Accounts-->>UC: Account entities
  UC-->>Client: consent-filtered account summaries
```

Provider synchronization (when used) is an **ingestion / background concern**, not part of the synchronous AIS GET path. Local demo data is loaded via Prisma seed.

## Transactional outbox

```mermaid
flowchart LR
  UC[Use Case] --> UoW[Unit of Work]
  UoW --> PG[(PostgreSQL)]
  UoW --> OB[(Outbox Table)]
  WRK[Outbox Worker] --> OB
  WRK --> KF{{Kafka}}
  WRK -->|failure| DLQ{{DLQ Topic}}
```

Domain events are persisted in the same transaction as aggregate changes. A worker polls unpublished rows and publishes to Kafka with retry and dead-letter handling.

## Signing keys and JWKS

Runtime signing material is **environment-managed** (see [ADR 009](adr/009-signing-key-management.md)). There is no implemented operator `rotateKeys` command and no supported database-backed `SigningKey` rotation path in this release.

```mermaid
flowchart LR
  ENV[JWT_PRIVATE_JWK / JWT_PUBLIC_JWKS / JWT_ACTIVE_KID] --> TS[TokenService]
  TS -->|sign| JWT[Access / ID tokens]
  TS -->|GET /jwks| Public[Public JWK Set]
  Ops[Operator / Secrets store] -->|rotate externally| ENV
  Dev[scripts/generate-dev-keys.mjs] -->|dev only| ENV
```

| Concern                   | Current behavior                                             |
| ------------------------- | ------------------------------------------------------------ |
| Public keys               | Exposed at `GET /jwks`                                       |
| Private signing key       | Loaded from `JWT_PRIVATE_JWK` at process start               |
| Development keys          | Generated by `scripts/generate-dev-keys.mjs` / Compose env   |
| Production rotation       | External operational responsibility (redeploy with new JWKs) |
| Prisma `SigningKey` table | Reserved for a future improvement; not used at runtime       |

## Worker health

The API image default `HEALTHCHECK` probes `GET /health/live`. The Compose `worker` service **overrides** that check: `WorkerHeartbeatService` periodically probes PostgreSQL, Redis, and Kafka, then writes `/tmp/fap-worker-heartbeat`. `scripts/worker-healthcheck.sh` fails if the file is missing or stale. See [deployment.md](deployment.md).
